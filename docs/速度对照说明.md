# 如何比较训练速度

本仓库用于检查我们实际运行的训练实现。尚未在同样硬件、输入和训练配置下完成与 ReCamMaster 的受控速度对照，因此不能仅凭一次更新的耗时判定方法本身更快。

## 优先对齐的条件

| 项目 | 当前 A 续训 |
| --- | --- |
| 输入 | 单参考视频 + 单目标视频 |
| RGB / 每视频 latent | 81 帧，432×768 / 16×21×54×96 |
| DiT token 数 | 每视频 21×27×48；两个视频共 54,432 |
| 多卡方式 | 4 张卡各自完整处理不同样本，手动 all-reduce；不是 4 卡共同处理同一个上下文 |
| batch | 每卡 microbatch 1，累积 10 次，全局有效 batch 40 |
| 数据路径 | 训练读取已经编码好的视频 latent，不在线运行 VAE |
| 文本 | 已有参考描述直接读取；embedding 在线计算。缺少描述时可能在线生成 |
| 精度 | BF16 autocast，部分主干模块 FP32，FP32 optimizer masters |
| 训练参数 | self_attn / cam_encoder 名称匹配，包括相关 norm 和 modulation；其他参数冻结 |
| 激活检查点 | 每个 block 进行选择性检查点，保存 attention 算子结果，其他操作允许重算 |
| 优化器 | fused AdamW，lr 2e-5，梯度裁剪 1 |
| 评测 | 每 100 次参数更新暂停训练，做 64 个保留案例的评测 |

当前最近记录的约 65 秒/更新，对应全局 40 个训练样本，约 0.62 样本/秒；不包含独立评测时间，也不是单样本延迟。应同时比较每卡 microbatch 的计算时间、全局样本/秒、token 数、评测和保存开销。

`overnight_camera_abc.py` 中 `load_seconds` 的计时起点位于累积循环之前，终点位于最后一个 microbatch 的 forward 之前；它包含之前 9 次前后向计算，不能解释为数据读取耗时。这个快照保留了原始实现，未为了公开而更改运行逻辑。

## 损失和监督量

`context_layout.py` 使用 flow velocity MSE：`zt = (1-sigma)*z0 + sigma*noise`，目标为 `noise-z0`。参考视频保持干净，只有目标区域计算误差。归一化仍对整个参考和目标拼接张量取均值，因此参考数量改变会改变损失尺度。当前没有额外的相机位姿、深度或重投影训练损失。

## 快速定位源码

- 前后向和累积：`overnight_camera_abc.py` 中 `train`。
- 多卡梯度通信：同文件 `sync_gradients`。
- 激活重算策略：同文件 `contexts`。
- CPU latent 读取、校验和相机射线计算：`data.py`。
- 在线文本计算：`text.py` 和 `basic_full_data.py`。
- 训练参数数量和冻结规则：`camera_backbone.py`。
- 历史单 microbatch 训练和预读尝试：`train.py`、`train_fast.py`、`input_pipeline.py`；这些不是当前 A 续训入口。

这是研究代码快照，含本机绝对路径、既有 manifest 和 checkpoint 协议依赖；不能直接 clone 后原样启动。README 所列 upstream 版本和环境清单供审阅依赖使用，未包含运行所需全部外部源码、数据或权重。
